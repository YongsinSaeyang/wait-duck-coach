等等鴨投資研究筆記庫的工作規則

這份文件適用於整個專案。開始修改前，先讀這份文件、README.md、content/sources.json，以及一篇現有筆記。若子目錄之後有更具體的規則，再一起遵守。

專案目的

替剛開始接觸量化投資的讀者整理可回查、可重做的教學筆記，逐步累積投資研究方法。每篇解決一個具體問題，例如沒有成交的 0% 報酬代表什麼。讀者可以從概念、教學計算和實作觀察理解研究限制。文字用繁體中文、像同學一起讀筆記，保留使用者真的提供過的經驗。

檔案與產出

  • 原始筆記放在 content/notes/YYYY-MM-DD-english-slug.md。
  • 所有外部資料來源登記在 content/sources.json，來源 ID 使用小寫英文與連字號。
  • 新筆記從 templates/note.md 複製，完成後必須移除所有佔位文字。
  • content/examples.json 登記每篇的數字運算、預期值與正文顯示值。算術由程式重新執行。
  • 作者提供的實測觀察放在 content/observations/，保留原話與證據範圍。可重現教學輸入放在 content/experiments/，計算結果與 SVG 放在 assets/。
  • 共用版面和 Markdown 轉換在 scripts/build.py。共用視覺在 assets/site.css，搜尋、分類、收藏及教學試算在 assets/site.js。
  • 執行 python3 scripts/build.py，產生根目錄 index.html、notes/slug.html 和 assets/notes.json。每篇筆記必須有自己的網址。
  • index.html 與 notes/*.html 是產物。修改內容時回到 Markdown，修改結構時回到建置程式，再重新產生。
  • 原始資料、模板、規則、建置程式和產物都需要提交到 GitHub。GitHub Pages 由 main 的根目錄發布，根目錄保留 .nojekyll。

每篇必須有的內容

檔案以兩條 --- 包住 JSON metadata。必填 id、title、date、updated、category、tags、summary、sources、related、origin、example_kind、experience_record、experiment。日期為 YYYY-MM-DD。id 必須與檔名的英文 slug 相同。

category 只能使用「量化入門」、「回測實作」、「研究方法」。tags 為 1–4 個不重複的短標籤。summary 30–120 個字。sources 列出登記過的來源 ID。related 列出 1–3 篇存在的筆記 ID，不能指向自己。origin 說明內容是作者提供的實測、程式推導，或公開文件整理。example_kind 目前固定為 teaching。experience_record 為作者觀察 JSON 的專案相對路徑，沒有個人觀察時填 null。experiment 可為 null，或填 script、input、output、chart 四個現有檔案的路徑。

正文依序包含四個二級標題，名稱保持一致。

  1. 我想釐清的問題
  2. 一個算得出來的例子
  3. 我會怎麼檢查
  4. 還需要注意什麼

正文可用三級標題、條列、表格、程式區塊，以及 [文字](https://官方頁面網址) 連結。每篇至少有一個可驗算的數字例子或可操作的檢查步驟。例子如為假設，當段就標明「教學假設」。日行情、績效和個人經驗不可自行補寫。每節正文至少 45 個非空白字元，檢查段落至少兩條可操作步驟。這些長度和關鍵字檢查只是最低門檻，仍要人工讀過內容。

資料與引用

先讀來源再寫。優先引用官方文件和原始研究。新增來源要記錄 title、publisher、url、checked，checked 為實際讀取日期。來源頁未讀到相關內容時，標記待查並換用可確認的資料。

每個 sources 中的來源都必須在正文中實際連結，正文的外部引用也必須登記。來源 ID 會在文章末尾產生來源卡，檢查器會分開列出未引用來源與檔案連結統計。筆記間的延伸閱讀用 related，網站另自動產生「哪些筆記連到這裡」的反向連結。作者編寫的 related 可以是單向，產生的回鏈必須存在。

財務計算用程式或明列公式驗算。單位、百分比、持有期間、成本和資料範圍要寫出來。百分比計算以小數進行，顯示時轉回百分數。0、負值和缺值分別處理。

找不到支持關鍵主張的來源時，先保留待查事項，該草稿不進入發布目錄。數值與來源矛盾時，列出兩者差異，等人工核對後再發布。算術與引用 ID 通過，只能說明計算與格式檢查通過。來源是否支持敘述、觀察是否真由作者提供，都要另外閱讀覆核。

描述執行結果時，區分「資金不足未建立模擬單」、「模擬單已建立但未成交」和「已成交」。本地試算紀錄不自動代表送到券商的委託。

公開內容以概念與教學假設為主。若使用者之後提供帳戶、金鑰或私人研究，先詢問哪些欄位可公開，再整理成可發布內容。

視覺與互動

奶油白背景、深綠文字、杏色重點，搭配小鴨引導。桌面保留導覽與閱讀欄，手機可自然換行。卡片統一顯示類別、日期、標題、摘要、標籤及閱讀連結。按鈕與連結需有清楚的鍵盤焦點，輸入框需有標籤。

每篇沿用同一文章模板，包含摘要、正文、來源、相關筆記與返回首頁。搜尋要涵蓋標題、摘要、標籤和正文。搜尋與分類可同時使用。收藏存於本機，失去本機儲存權限時仍能閱讀。

新增一篇的工作順序

  1. 讀規則、模板、來源登記及兩篇相關筆記。
  2. 確認使用者想解決的問題，整理已提供的觀察。缺少事實就寫待查或追問。
  3. 查證官方來源，更新 content/sources.json。
  4. 複製模板，填好 metadata 和四節正文，選擇相關筆記。
  5. 更新例子登記，執行 python3 scripts/build.py、python3 scripts/check.py、python3 -m unittest discover -s tests -v，以及 python3 scripts/execution_demo.py --check。
  6. 預覽新文章及首頁。檢查搜尋找到新文章、來源可點開、相關連結有效和手機版可讀。
  7. 在 CHANGELOG.md 記錄真的修改了什麼、跑過什麼檢查。沒有執行的測試應標為尚未測試。
  8. 一起提交原始 Markdown、登記資料和產物。GitHub Actions 在 push／PR 執行相同檢查，發布工作必須等待驗證成功。正式站使用 GitHub Actions 發布來源。

完成條件

新增文章可以只改內容與來源檔，沿用建置程式產生相同風格。發布前必須通過 schema、重複 ID、來源 ID、關聯 ID、必要段落、日期、內部檔案路徑與產物一致性檢查。若建置失敗，先修正來源，保留失敗訊息作為修改紀錄。尚未核實的網址、測試、部署結果不得寫成已完成。

內容檢查會攔截佔位文字、缺少教學標示、未引用來源、沒有依據的第一人稱實測敘述，以及與登記算術不符的結果。PASS 不代表 AI 已核實所有研究主張。小螢幕至少測 320、360、390px，試算結果需有 aria-live 狀態區。
